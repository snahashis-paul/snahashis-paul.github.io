01 · OTORideCloud infrastructure

Moving a micromobility
platform to Amazon EKS.

Migrated services from traditional servers to Docker, then to Terraform-defined EKS infrastructure supporting HTTPS and vehicle TCP traffic.

AWS EKSTerraformDockerIstio
Read case study +

The challenge

OTORide’s micromobility platform needed an infrastructure path from traditional servers to containerised services, with routing for both web requests and vehicle TCP traffic.

My contribution

  • Moved services into Docker and then onto Amazon EKS.
  • Defined the EKS infrastructure using Terraform.
  • Used Istio to route HTTPS and vehicle TCP traffic.
  • Configured nodes to be added on demand.

The outcome

The migration lowered monthly AWS costs. The platform’s infrastructure could be described in code, alongside containerised service deployment.

02 · OTORideRelease automation

GitOps delivery with
Helm and Argo CD.

Connected a monorepo release pipeline to versioned Helm charts and automated cluster synchronisation, with short-lived registry credentials.

HelmArgo CDECRExternal Secrets
Read case study +

The challenge

Deliver releases from a monorepo to Kubernetes through a repeatable process, while avoiding long-lived registry keys in the cluster.

My contribution

  • Set up custom version bumping in the monorepo release pipeline.
  • Published Helm charts to Amazon ECR.
  • Configured Argo CD to sync releases with automatic pruning and self-healing.
  • Configured External Secrets Operator with IAM roles for service accounts to obtain short-lived ECR credentials.

The outcome

Versioned charts and GitOps synchronisation connected the release pipeline to the cluster. Registry access used short-lived credentials instead of stored long-lived keys.

Engineering focus

Release versioning, reconciliation and credential lifecycle are all part of operating the delivery system.

03 · OTORidePlatform reliability

Addressing recurring
Elasticsearch failures.

Investigated resource-related Elasticsearch failures that caused incomplete API responses, and added practical measures to improve reliability.

ElasticsearchDockerCI/CDELK
Read case study +

The challenge

Recurring Elasticsearch failures affected API responses. The failure modes included JVM heap exhaustion, circuit-breaker trips and full disks.

My contribution

  • Tuned JVM heap settings.
  • Added scheduled log clean-up jobs through CI/CD.
  • Used Docker monitoring to support operation of the services.

The outcome

These changes addressed the recurring failures. My wider infrastructure work also included logging pipelines built with Kafka, Logstash and the ELK stack.

Engineering focus

Investigating memory, disk usage and application symptoms together helped connect infrastructure failures to their impact on users.
